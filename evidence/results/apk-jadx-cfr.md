# APK / DEX decompilation: disrobe vs JADX vs CFR

- id: `apk-jadx-cfr`
- ecosystem: android
- claim: On their respective committed EdgeCases inputs, disrobe recovers at least as many recompile-clean main-class methods as JADX on DEX and CFR on JAR under real javac, with no original-jar classpath leak.
- measured: Android DEX: `disrobe` 129 / 132 (97.7%) vs JADX 128 / 130 (98.5%); JVM classfile: `disrobe` 131 / 131 (100.0%) vs CFR 105 / 106 (99.1%)
- oracle strength: recompile-only
- CI-attested: yes [CI]
- evidence basis: real javac (JDK), per-method recompile error-free against a STUBBED (empty) classpath so a wrong recovered signature cannot resolve against the original classes; the SAME oracle scores every tool
- reproduce: `cargo run --locked -p disrobe-bench-head-to-head -- --check --only apk-jadx-cfr`
- floor: 95.00 (holds)
- gate source: evidence/results/measured/apk-jadx-cfr.json (regenerated by cargo run -p disrobe-bench-head-to-head)
- note: Needs javac, jadx, and cfr on PATH, with cfr.jar provisioned by evidence/competitors/install-linux.sh. Recompile-only: each method body compiles clean, not asserted byte-equivalent. The DEX leg compares disrobe with JADX on EdgeCases.dex; the JAR leg compares disrobe with CFR on EdgeCases-baseline.jar, because CFR cannot read DEX. The STRONG asserted JVM number is the 131/131 per-method recompile gate (jvm-javac descriptor). Both decompilers emit synthetic accessor/lambda/bridge methods, so the per-tool emitted-method count differs by design; the claim therefore compares clean-method counts within each leg while reporting recompile-clean rates alongside them.
