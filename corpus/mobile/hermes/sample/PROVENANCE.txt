disrobe self-authored benign React Native Hermes bytecode sample
================================================================

Source: sample.js (plain JavaScript, no third-party packages, no network, no
eval). Authored for disrobe regression fixtures. It exercises arithmetic
(add), a counted loop (sumRange), string concatenation (greet), and a class
with prototype methods (Counter.increment / Counter.label), plus an entry
function (main).

Compiler: the real Hermes compiler (hermesc), FOSS, from the official
facebook/hermes GitHub release binaries (hermes-cli-windows). Each .hbc here is
the raw output of `hermesc -emit-binary`. The bytecode is never executed; it is
parsed and lifted statically.

Exact build command (per version, run against the matching compiler executable):

  <compiler>.exe -emit-binary -out sample.hbc.<version> sample.js

The v62, v71, v74, v83 and v89 artifacts were built from a directory holding only
sample.js, with the input named relatively, so the module source path they record is
"sample.js" and no host directory appears in the file. The three older artifacts
record "C:\workdir\AppData\Local\Temp\hermes-scratch\sample.js" from an earlier build.
Neither spelling changes the recovered program.

upstream-disasm/hbc<version>.txt

  The disassembly the matching Hermes release prints for the committed bundle at
  that version, produced by running that release against the committed file:

    hermes.exe -b -dump-bytecode sample.hbc.<version>

  Each file holds the tool output from its first line up to, but not including,
  the first line beginning "Debug ". Nothing else is edited. The debug tables are
  dropped because they carry the build-time source path of the three older
  artifacts and say nothing about opcode numbering.

  crates/disrobe-pass-mobile/tests/hermes_upstream_disassembly.rs compares the
  instruction names disrobe decodes against the names the release prints, per
  function, for every committed version.

Scope of recovery:

  Container parse (header, function table, string and identifier tables) works
  across the committed v62-v96 spread: all eight resolve 8 functions and recover
  the real function names add / sumRange / greet / Counter / main / increment /
  label from the module string table.

  Opcode lifting runs through a per-version opcode table, one per committed
  artifact, each transcribed from include/hermes/BCGen/HBC/BytecodeList.def at
  the facebook/hermes tag whose BYTECODE_VERSION matches. Every artifact lifts
  every function at zero declined opcodes, and every recovered body reproduces
  the behavior of the matching function in sample.js when both are run in the
  boa JavaScript engine. That differential is the gate at
  crates/disrobe-pass-mobile/tests/real_hermes_correctness.rs.

  Instruction counts differ across the spread because the compilers differ, not
  because recovery does: 161 at v62 and v71, 98 at v74 through v89, 99 at v96.
  The two oldest releases keep locals in an environment and pass call arguments
  through the frame window, which the later releases optimise away.

  This is a structured lifter, not a full decompiler. Call and Construct recover
  arguments from the bounded frame-register window when every register has a
  materialized value. CallDirect and CallBuiltin, and any incomplete frame window,
  retain one <arg?> marker per argument. Instrumentation opcodes such as
  ProfilePoint and AsyncBreakCheck count as fallback, not reconstruction.
